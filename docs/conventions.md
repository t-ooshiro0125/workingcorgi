# 開発規約

## 実装

- ページは `src/pages/`、再利用するコンポーネントは `src/components/`、レイアウトは `src/layouts/` に置く。
- Astro コンポーネントのファイル名は PascalCase、ページのファイル名は URL を表す小文字の名前にする。
- まずは Astro と SCSS で実装する。新しい UI フレームワークや依存関係は、必要性を確認してから追加する。
- 公開サイトに機密情報、個人情報、アクセスキーを含めない。

## スタイル

### 基本

- 厳守: SCSS を使う。Sass の読み込みには `@use` を使い、`@import` は使わない。

### 配置

- 原則: スタイルは対象に近い場所に置く。
  - グローバルスタイルは `src/styles/index.scss` に集約し、`Layout.astro` で一度だけ読み込む。
  - ページ・コンポーネント固有のスタイルは対応する `.astro` に置く。
  - 共通 UI は `src/styles/components/` に置く。
  - サイト全体の基盤スタイルは `src/styles/foundation/` に置く。
    - `_tokens.scss`: CSS 変数
    - `_reset.scss`: リセット
    - `_base.scss`: 基本スタイル
  - CSS を出力しない共通処理は `src/styles/tools/` に置く。

### セレクタ

- 原則: 共通 UI は BEM のクラスで指定する。
- 例外:
  - `src/styles/foundation/` では要素セレクタを使ってよい。
  - ページ・コンポーネント内の固定マークアップには要素セレクタを使ってよい。必要に応じて `>` で直下に限定する。
- 厳守:
  - 独自の表示状態と再利用には BEM のクラスを使う。
  - BEM の要素は `__`、状態とバリエーションは `--` で表す。
- 見た目に関係しない JavaScript 参照には `data-*` を使う。

### 記述

- 変数は次のルールに従う。
  - CSS: `--color-*`、`--space-*`、`--font-*` で命名する。
  - Sass: コンパイル時だけ必要な値に使う。
- 原則:
  - ネストは浅く保つ。
  - `!important` とページ側からの共通スタイル上書きは避ける。
  - `&` は疑似クラス・疑似要素と同一要素の状態だけに使う。
- 厳守: プロパティ順は `stylelint.config.mjs` に従う。

## 記事とコンテンツ

- 記事の公開日時、タイトル、概要、タグなどのメタデータは、実装するコンテンツコレクションのスキーマに従う。
- 外部サイトへのリンクは、公開前にリンク先と表示内容を確認する。
- 画像、引用、ライセンスが必要な素材は、利用条件を確認してから使う。

## Changelog

### データ管理

- 原則: Changelog の項目は `src/data/changelog.ts` で一元管理し、更新日の新しいものから表示する。
- 必須項目:
  - `date`: 更新日を `YYYY-MM-DD` 形式で設定する。
  - `title`: 更新内容を簡潔に表すタイトルを設定する。
  - `description`: 閲覧者にとって何が変わったかを短く説明する。
- 任意項目: 関連するページやプロダクトがある場合は、次のどちらかを `link` に設定する。
  - サイト内ページ: `kind: "internal"` と、`BASE_URL` 配下の相対パスを `path` に設定する。
  - 外部プロダクト: `kind: "external"` と、`https://` URL を `url` に設定する。
- 内部リンクの `path` には、絶対パスや `.`、`..` を含むパスを設定しない。

### 掲載判断

- 原則: 閲覧者にとって意味のある主要な変更を掲載する。
- 対象:
  - ページ、主要機能、プロダクトの追加や大きな更新
  - サイト構成やデザインなど、閲覧体験に大きく影響する変更
  - 重要な不具合修正や、公開・運用に関する閲覧者への影響が大きい変更
- 対象外:
  - Notes の記事追加や、軽微な文言・デザイン修正
  - 閲覧者への影響が小さい不具合修正やリファクタリング
  - 依存関係、CI、開発環境など、閲覧者に直接影響しない内部変更
  - Git のコミットや Pull Request の網羅的な記録

### 追加手順

1. 変更内容が掲載対象に該当するか確認する。
2. 該当する場合は、原則として同じ Pull Request で `src/data/changelog.ts` に項目を追加する。
3. 関連先がある場合は、サイト内ページには `link.kind: "internal"` と `link.path`、外部プロダクトには `link.kind: "external"` と `link.url` を設定する。
4. Home の最新 5 件と `/changelog/` の全件一覧で、表示順、内容、リンク先を確認する。

## 単体テスト

### 対象と配置

- 原則: TypeScript の純粋な関数を対象にする。
- 配置: 対象モジュールと同じディレクトリに配置する。
- 命名: `*.test.ts` とする。

### 実行環境

- 原則: Dev Container と CI の標準である Node.js 24 を使用する。
- 例外: ブラウザ API を使うテストが必要になった場合は、DOM 環境などの追加依存を検討する。

### 実行方法

- 単発実行: `npm test`
- 継続実行: `npm run test:watch`

## 検証

### 実装変更後

- 原則: 変更内容に応じて次のコマンドを実行する。
- コマンド:
  - `npm run format:check`
  - `npm run lint`
  - `npm test`
  - `npm run build`

### コミット前

- `git diff --cached` を確認し、不要なファイルや機密情報が含まれていないことを確認する。

## コミットメッセージ

- `feat`: 機能追加
- `fix`: バグ修正
- `docs`: 文書変更
- `style`: 動作に影響しない書式・整形の変更
- `refactor`: 動作を変えない内部整理
- `test`: テスト変更
- `ci`: CI 設定の変更
- `chore`: 環境構築・設定・依存関係の変更
